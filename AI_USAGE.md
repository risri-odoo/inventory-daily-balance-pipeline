After Phase 2: the future-dated rule now compares against the local calendar date written in event_ts, not its UTC date. Example: 2026-02-04T01:00:00+05:30 with business date 2026-02-04 must be valid. Commit fca5359, assumption A10.

Problems found and fixed during the build (facts from the build)
Incremental rebuild barely faster than a full rebuild (1.1×). Found by the first 100k benchmark: both read the whole ledger. Fixed with a filterable NOT EXISTS view, two indexes, and reading only the affected pairs. The speed-up became 3.2×, and the 100k load went from 48 s to 22 s. Commits 14f3e36 (baseline) and 87d9b1a (fix).
Intermittently failing test, caused by random run order. Runs were ordered by a one-second timestamp plus a random run_id suffix. They are now ordered by insertion order. Commit 02b0b05.
Process mistake: commits 87d9b1a and 27b469d were pushed while that intermittent test was failing. The assistant's shell command checked the exit status of tail instead of pytest. The fix followed within minutes, and every later push was gated on pytest's own exit code.
Mutation checks: in Phase 3, two key lines were deliberately broken in a scratch copy to confirm the tests catch them. They did.
Dashboard escaping test gap (Phase 8):
A mutation check showed that removing html.escape from the dashboard failed no test, because the hostile test data only reached the embedded JSON.
A test now puts a hostile value into a server-rendered section (the run log's error_message), and both escaping mutations (HTML and JSON) fail the intended tests.
The template filling was also changed to a single pass, so data containing a placeholder name such as __DATA__ cannot be replaced.

Disagreements with the AI, and bugs I caught (candidate)
Future-dated rule (A10): overrode the assistant's choice. Claude Code's version compared business_date with the UTC date of event_ts. In review we found that this wrongly rejects valid India-time records: a sale at 2026-02-04T01:00+05:30 is still 2026-02-03 in UTC, so a same-day business date of 2026-02-04 was rejected as FUTURE_DATED. A business date is a local business day, so I had the rule changed to compare against the local date written in the timestamp, and a test case added (fca5359).
Repository location: overrode the planning chat. It recommended reopening Claude Code directly inside the cloned repo folder. I judged the nested location harmless because commits and pushes worked, and kept it. The only risk was CLAUDE.md not loading in a new session, which I handled by pointing new sessions at it.
History rewriting: decided against it. The assistant pushed two commits while a test was failing (it disclosed and fixed this itself in 02b0b05), and my git email appears in the commit metadata. Fixing either would mean rewriting history, which would also damage the commit-timestamp evidence. I chose to leave the history as it is and disclose both here.
Generator realism: accepted a known limitation. The generator never produces negative stock (late rows are issues only, and corrections only increase quantities, see A28). I accepted this because negative stock, voids, out-of-order versions and location-changing corrections are covered by the hand-made sample instead. The limitation is listed in the README.
