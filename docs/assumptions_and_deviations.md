# Assumptions and deviations

Every assumption made where the spec was silent, and every deviation from the spec, is recorded here.

## Assumptions

| # | Area | Assumption | Why |
|---|------|------------|-----|
| A1 | Balance components | In `daily_inventory_balance`, `issue_qty` and `transfer_out_qty` are stored as positive magnitudes; `adjustment_qty` is signed. So `net_change_qty = receipt_qty - issue_qty + transfer_in_qty - transfer_out_qty + adjustment_qty`. | Positive magnitudes read naturally in reports ("issued 5"); adjustments can go either way so they keep their sign. |
| A2 | Default paths | `INV_DB_PATH` defaults to `output/inventory.db` and `INV_OUTPUT_DIR` to `output`, both relative to the current directory. | Keeps all generated artefacts in one git-ignored folder. |
| A3 | Foreign keys | The tables do not declare SQLite foreign keys. Validation rejects unknown SKUs and locations, and a reconciliation check confirms there are no orphans. | Keeps loads simple and makes the orphan check an explicit, visible data-quality control. |
| A4 | File format | Files are UTF-8 (a BOM is ignored), comma-separated, with **one record per physical line**. Quoted values may contain commas but not line breaks. | Lets every row keep its exact `source_line` and original `raw_record` for tracing. Movement feeds rarely contain multi-line values. |
| A5 | Blank lines | Fully blank lines are skipped and not counted in `rows_read`. | Trailing blank lines are common in exported CSVs and carry no data. |
| A6 | Header matching | Header names are matched after trimming spaces and lower-casing (`" SKU "` matches `sku`). A name that repeats after this normalisation counts as a duplicate column. | "Matched by header name" should not depend on cosmetic differences. |
| A7 | Zero-byte file | A zero-byte (or whitespace-only) file has no header; it is treated as a successful empty batch, not as a file with missing columns. | The spec says a zero-byte file is a successful empty batch. |
| A8 | Unknown destination | An unknown `to_location_id` is rejected as `UNKNOWN_LOCATION` (an invalid reference key). A TRANSFER with a blank `to_location_id`, a destination equal to the source, or a destination on a non-transfer row, is `INVALID_TRANSFER`. | Keeps one code per kind of problem: reference errors vs. transfer-shape errors. A blank destination is not `MISSING_REQUIRED_FIELD` because the column is only required for transfers. |
| A9 | Timestamps | `event_ts` must contain a date **and** a time (`YYYY-MM-DDTHH:MM[:SS[.fff]]`, `T` or space). A date alone is `INVALID_TIMESTAMP`. Offsets are converted to UTC; no timezone means UTC. Stored as `YYYY-MM-DDTHH:MM:SSZ`, keeping fractional seconds only if present. | A timestamp without a time is ambiguous. Keeping fractions avoids two different source timestamps collapsing to the same value. |
| A10 | Future-dated check | Compares `business_date` with the **local calendar date as written in `event_ts`** (before converting to UTC). Example: `2026-02-04T01:00:00+05:30` with `business_date` 2026-02-04 is valid, even though the UTC date is 2026-02-03. With no timezone the local date is the UTC date. `event_ts` is still stored in UTC. | The business date is set where the event happens, so the source's own calendar day is the fair comparison. Comparing with the UTC date wrongly rejected same-day events from timezones ahead of UTC. (Changed after Phase 2 at the candidate's request, see the prompt log; the first version used the UTC date.) |
| A11 | Check cascade | A check is skipped when the value it depends on already failed (e.g. a non-numeric quantity is not also range-checked; an unknown movement type skips the sign and transfer checks). If `version` is invalid, the quantity sign rule is applied as if it were version 1. | All real failures are still recorded, without confusing follow-on errors. |
| A12 | Payload hash | `payload_hash` = SHA-256 of the normalised business values: movement_type, sku, location_id, to_location_id, quantity, business_date, event_ts (UTC), reason_code, source_system. The key (`movement_id`, `version`) is not part of it. | Two rows with the same key are exact duplicates when these values match after normalisation (so `receipt` vs `RECEIPT`, or `Z` vs no timezone, are not treated as conflicts). |
| A13 | Number formats | Quantity and version must be plain whole numbers: `1.5`, `1e3`, `1,000` and `1.0` are rejected. A leading `+` is accepted on quantity. | "Integer only" in the spec; refusing to guess at formats is safer for stock data. |

| A14 | Duplicate rows | `DUPLICATE_EVENT` rows are also written to `quarantine_movement` (reason `DUPLICATE_EVENT`) but counted in `rows_duplicate`, not `rows_rejected`. The details name the run, file and line of the first arrival. | Keeps every input row traceable, and lets reconciliation check `rows_read = accepted + rejected + duplicate` against real table counts. |
| A15 | Duplicate vs. invalid | The duplicate check runs only on rows that pass validation. Only accepted rows can be a "first arrival". | Matches the reject-code order (duplicate codes are last), and an invalid row never entered history. |
| A16 | Late cutoff | A row is late if its `business_date` is before the max `business_date` in `movement_event` **before the current file started**. Rows of the same file do not make each other late. | Rows in one file have no reliable order, so lateness is judged against what was already loaded. |
| A17 | Global horizon | The horizon is `MAX(business_date)` over **all** rows in `movement_event` (all versions). It never moves backwards. | History is append-only, so the horizon is stable and incremental rebuilds never need to delete rows past it. |
| A18 | Pair existence and start | A pair exists if it has an opening balance or at least one current ledger leg (a voided qty-0 version still counts as a leg). It starts on `as_of_date + 1`, or on its first current movement date. If a correction moves a pair's only movement elsewhere, its balance rows are deleted. With no movements at all there is no horizon, so no balance rows. | Keeps incremental and full rebuilds identical: both derive pairs from the same rule. |
| A19 | Legs inside a closed period | Validation rejects them, but if a later opening-balance change puts already-loaded movements on or before the new `as_of_date`, those legs are ignored by the balance build (they are treated as included in the snapshot). | The opening balance is the authoritative on-hand at the end of `as_of_date`. |
| A20 | `negative_balance_rows` | Counts negative `closing_qty` rows in the **whole** balance table after the run, not just the rows this run wrote. | Shows the current data-quality state after every run. |
| A21 | Folder runs | Files are processed in filename order. Processing stops at the first `FAILED` file so later batches are never loaded ahead of it. A `REJECTED` file (bad header) does not stop later files. | A failure is usually transient (retry), a rejected file needs fixing at the source. |
| A22 | File identity | `processed_file` is keyed by content hash: a renamed copy of a processed file is `SKIPPED`. With `--force`, the original `processed_file` row (first run_id) is kept. | Idempotency follows content, not names. |
| A23 | Reference loads | Reference files are trusted master data: any bad value fails the whole load (rolled back) instead of quarantining rows. Upserts never delete rows missing from a newer file. Each load is logged as a `pipeline_run` with `source_file = 'reference'`. | Master data errors should stop the line; deletes of master data are out of scope. |
| A24 | IDs and timestamps | `run_id` = `run-<UTC yyyymmddThhmmssZ>-<8 hex>`: unique, and readable as a time, but only ordered to the second (the suffix is random). Reports, exports and checks therefore list runs in insertion order (`rowid` of `pipeline_run`), never by `started_at` or `run_id`. `ingested_at` / `quarantined_at` use the run's start time, so all rows of one run share one timestamp. | Two runs can start in the same second. Ordering by timestamp + run_id made the run order random in that case; this showed up as an intermittently failing test after Phase 6 and was fixed. |

| A25 | Demo database | `demo` always uses and recreates `<output-dir>/demo.db` and has no `--db` option. Reports go to the output dir. | "A fresh DB" every time, without any risk of wiping the database the other commands use. |
| A26 | Extra reconciliation check | Besides the checks in the spec, `closed_period_legs` WARNs if an accepted leg is dated on or before its pair's opening `as_of_date` (only possible if an opening balance changed after loading, see A19). `pair_coverage` also checks each pair *starts* on the right date and that no unexpected pairs exist. | Makes the A19 exclusion visible instead of silent, and proves the dense grid end to end. |
| A27 | Report exit code | `reconcile`, `report` and `demo` exit with 1 when any check is FAIL. WARN (e.g. negative balances) still exits 0. | The spec treats negative stock as a warning, not a failure. |

| A28 | Generator: safe defects | Late arrivals are only ISSUE rows (moved 1–2 batches later). Receipt corrections only **increase** the quantity. Conflicting duplicates differ only in `reason_code`. | A late receipt, or a correction that lowers a receipt, could make a later day negative even though the "true" stock never was. Changing only `reason_code` keeps the conflicting copy otherwise valid, so its only possible outcome is `CONFLICTING_DUPLICATE`. |
| A29 | Generator: labels | The generator simulates processing order to write per-row expected rejects (file, line, movement_id, reason), per-batch counts (read/accepted/rejected/duplicate/late) and final closing balances at the horizon, all in `labels/` outside `input/`. The final-balance oracle comes from the generator's own event list, not from pipeline code. | A stronger oracle than counts alone, while still independent of the pipeline. |
| A30 | Generator: row count | `--rows` is the exact number of data rows across all batch files (base events + corrections + duplicates + conflicts + invalid rows). It can come out lower only if there are fewer receipts than requested corrections, which does not happen with the defaults. | Makes "100,000 rows" literal. |
| A31 | Incremental read | The incremental rebuild reads ledger legs only for the affected pairs (plus opening-only pairs that have no rows yet). Unaffected pairs are extended by carrying their last closing forward. This relies on the invariant that a pair with movements always has balance rows (it was affected when they loaded). The `pair_coverage` reconciliation check would catch any violation. | Measured in `docs/benchmark.md`: the incremental late-batch rebuild went from 3.3 s to 0.29 s at 100k rows. |
| A32 | View definitions | `v_movement_current` uses `NOT EXISTS (a higher version)`. Views are dropped and recreated on every `init`, so older databases pick up the current definitions. Tables are never dropped. | Same meaning as the original `GROUP BY` join, but faster and filterable. Views hold no data, so recreating them is safe. |

| A33 | Dashboard data size | The dashboard embeds every balance row, movement version and quarantine row as JSON, so the page needs no server. Measured: 27 KB for the sample, 13.8 MB (built in 5.6 s) for the 100k benchmark database. The quarantine table shows at most 500 matching rows at a time. | Meant for review-sized databases. For large ones, the next step would be embedding only summaries plus a chosen subset of pairs. |
| A34 | Dashboard "read-only" | The dashboard writes nothing to the data. Like every other command it opens the database through the shared helper, which creates missing tables and recreates the two views (definitions only, no data). The `demo` command writes the dashboard after the report. | Lets the dashboard open an empty or older database without special cases; data is never modified. |
| A35 | Dashboard rendering | Static sections (header, check cards, run log, reject counts) are rendered in Python with `html.escape`. Interactive sections are drawn by JavaScript using only `textContent`. The JSON block escapes `<`, `>`, `&`, U+2028 and U+2029. The SVG chart takes its namespace from a static `<svg>` element in the page, so no namespace URL appears in the file. | Defence in depth against hostile values in `raw_record`, and the file stays strictly offline (no `http`/`https` anywhere). |

## Deviations

| # | Spec | What was done | Why |
|---|------|---------------|-----|
| D1 | Module list in section 13 | Added two small modules not in the list: `load.py` (event loading and duplicate/version handling) and `logs.py` (key=value logging). | Keeps `pipeline.py` focused on orchestration and each module small enough to explain on its own. |
